One column is a true head-to-head; the rest is empty space. IBM’s playground set and the scenarios config of the 467 are the same 152 scenario ids — verified, not assumed — so the 152 column is the only place IBM and we answer identical questions. Everywhere else the two sides never meet: IBM never ran the 467, the 88, or the 40; we never ran A, B, D, or E on the 152.
And the gaps on our own side are the finding. A and B — the two arms that carry the entire “inverted LLM” argument — were never run on the 467. C is the only architecture evaluated everywhere. D (GAK) exists only on the 88, which is a subset of the 467 — so C and D answer the same 88 questions by different means, a comparison the paper never makes. Note also that IBM’s Plan-and-Execute covers only 124 of the 152; that cell is not full coverage.
Architecture A does not exist. The paper’s baseline — the 65% that the headline “+17 points, same model” is measured against — was never run by us on the 139. That number is cited from IBM’s paper: their harness, their grader, their undisclosed model. And the one cell where A was run (custom-40, 85%) is not a document baseline at all: benchmark/run_baseline.py loads no CouchDB, no CSV, no JSON, and calls no tools — it sends a single LLM call instructing the model to “answer based on general industrial knowledge.” So a model with no data access whatsoever scored 85% on the scenarios we called “structurally impossible with flat document stores.” A run that builds the real Architecture A — IBM’s agent, IBM’s documents, a named model, our grader — is in progress (docs/ARCH-A-PROTOCOL.md).

Read the metrics, not the numbers. IBM’s Agent-as-Tools figure is a trajectory judged “Accomplished” by an LLM judge (Llama-4-Maverick-17B); their Plan-and-Execute figure is task-completion under their 3-axis rubric. Ours is a harness pass-scorer on a final answer. A higher number on our side does not mean a better agent — it means a different question was asked. The only apples-to-apples comparison in the paper is the rubric re-scoring of Architecture B.

03bThe data-layer effect, isolated at last

The paper’s headline — “+17 points, same model” — compared its graph result against a 65% baseline it cited from IBM but never ran. We built that baseline (docs/AUDIT-2026-07-13.md): IBM’s ReAct agent over IBM’s CouchDB documents, gpt-4o, graded by Architecture B’s own grader. Only the data layer varies.

Comparison (gpt-4o, same grader)A: documents B: typed graphdata-layer Δ
all 139 scenarios 58.3%81.3% +23.0
95 data-path-matched scenarios excludes 44: 30 need an alert/anomaly server absent upstream, 14 reference assets in neither data layer 66.3%84.2% +17.9
The effect is real, and about the size the paper claims. On the scenarios where both sides genuinely have the data, the typed graph beats a document baseline by +17.9 points under an identical model and grader — positive across all five scenario types. The paper’s magnitude holds. What it lacked was this baseline: Architecture A as shipped loads no data at all, the 65% was never measured, and the graph side was tuned on the test set while the baseline got zero iterations.
Why 44 scenarios are set aside, and why that matters. The 139 are old-era scenarios; our graph was built from that old data; IBM’s current agent ships some of it away (no alert/anomaly server). Add a keyword grader that rewards naming entities over computing answers, and a perfectly-matched 139-wide comparison is not achievable by seeding — which is itself a finding the original paper never surfaced.
